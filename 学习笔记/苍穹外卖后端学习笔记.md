## 一、项目整体架构与模块划分

### 1.1 整体架构：前后端分离 + 后端内部三层

**前后端分离**：前端（Vue 小程序/网页）只管展示和收集用户操作，后端（这份 Java 代码）只管「处理业务 + 读写数据库」。两边通过 HTTP + JSON 通信。所以后端每个方法返回值大多包在 `Result<T>` 里，就是为了前端好统一解析。

**后端内部分层**（经典 MVC 的"甜点店"版）：

```
浏览器/小程序  →  Controller(服务员接单)  →  Service(后厨师傅做菜)
                    ↑                              ↓
               配置/拦截器(AOP门卫)             Mapper(采购员买菜/SQL)
                                                    ↓
                                              MySQL数据库(仓库)
```

分层目的就一句话：**每层只干自己那件事，改动一层不连累其他层**。

### 1.2 三个模块 sky-common / sky-pojo / sky-server 各放什么

这是个 Maven 多模块工程（父工程 sky-take-out 下有 3 个子模块）。用"搬家分箱"理解：**把所有代码按"用途"分装进不同的箱子**，谁要用就去谁箱子里 import。

**① sky-common（公共工具箱）**——放"**所有模块都可能用到的通用东西**"，不含业务：
- `result/Result.java` —— 后端统一返回结果的包装类（只有 `code/msg/data` 三个字段 + 静态方法 `success()/error()`）。
- `context/BaseContext.java` —— 基于 `ThreadLocal` 的"当前登录用户暂存器"，谁登录就把用户 id 塞进去，别处随时能取。
- 还有：`constant/`（各种常量如 `AutoFillConstant`、`MessageConstant`、`JwtClaimsConstant`）、`exception/`（一堆业务异常）、`enumeration/OperationType`、`properties/`（`JwtProperties` 等，读 yml 配置用）、`utils/`（`JwtUtil`、`AliOssUtil`、`HttpClientUtil`、`WeChatPayUtil`）、`json/JacksonObjectMapper`、`result/PageResult`。

> 判断标准：**"跟具体业务无关、只跟技术相关"**的 → common。

**② sky-pojo（数据传输箱）**——放"**跟数据库表和接口传参对应的裸数据类**"，只装数据不装逻辑：
- `entity/`（实体）：`Employee`、`Category`、`Orders`…… 一张数据库表一个，**字段和表列几乎一一对应**。
- `dto/`（前端传进来的参数）：`EmployeeLoginDTO`、`CategoryDTO`、`OrdersSubmitDTO`……
- `vo/`（返回给前端的组装结果）：`EmployeeLoginVO`、`OrderSubmitVO`……

三者区别（初学者最晕）：**entity = 数据库里的一张表的"照片"；dto = 请求进来时的"输入单"；vo = 响应出去的"账单"**。同一个字段可能三处都有，但"出场场景"不同。

**③ sky-server（餐厅本体/主程序）**——真正干活 + 装配一切的模块，启动类 `SkyApplication.java` 就在这。分层放：
`controller/`、`service/`、`mapper/`、`config/`（各种配置类）、`interceptor/`（JWT拦截器）、`aspect/`（AOP切面）、`annotation/`（自定义注解）、`handler/`（全局异常）、`task/`（定时任务）、`websocket/`。resources 下有 `mapper/*.xml`。

> 依赖方向永远是：server → pojo/common；pojo 和 common 谁也不依赖谁。这就是"高内聚、低耦合"。

## 二、分层详解（Controller → Service → Mapper → POJO）

### 2.1 每一层的"餐馆"比喻 + 职责

| 层 | 比喻 | 干的事 | 项目里的真实类 |
|---|---|---|---|
| **Controller** | 前台**服务员**：收菜单、把菜端给顾客 | 接 HTTP 请求、取参数、调 Service、把结果包进 Result 返回 | `EmployeeController` |
| **Service** | 后厨**厨师**：决定一道菜怎么做、管多道菜的先后 | 写业务规则、编排多步操作、控制事务 | `EmployeeServiceImpl` / `OrderServiceImpl` |
| **Mapper** | **采购员**：向仓库下单 | 把方法调用翻译成 SQL，管数据库交互 | `EmployeeMapper` + `.xml` |
| **POJO** | 传菜用的**托盘/单据** | 纯装数据，跑来跑去 | `entity/dto/vo` 里的类 |

对应到真实调用（员工登录）：

```
POST /admin/employee/login
   └─ EmployeeController.login()
        └─ EmployeeService.login(dto)         // 厨师
             └─ EmployeeMapper.getByUsername()  // 采购员 → SQL查数据库
```

### 2.2 Controller 层详解

**核心注解逐个拆：**

**`@RestController`** — 告诉 Spring「这个类是个 Controller，而且每个方法返回值自动转成 JSON 写回给前端」。它是 `@Controller` + `@ResponseBody` 的组合。
```java
@RestController          // 我是后端控制器，返回自动转JSON
public class EmployeeController {
    @GetMapping("/page")
    public Result page(...) { return ...; }  // 不用手动转JSON
}
```

**`@RequestMapping("/admin/employee")`** — 类上的**地址前缀**。下面所有接口的完整路径都拼这个前缀。
```java
@RequestMapping("/admin/employee")   // 本类所有方法URL都以它开头
```

**`@GetMapping` / `@PostMapping` / `@PutMapping`** — 指定方法处理的 HTTP 方式 + 具体路径，其实都是 `@RequestMapping(method=...)` 的快捷写法。
```java
@GetMapping("/page")   // 处理 GET /admin/employee/page
public Result<PageResult> page(...)
@PostMapping("/login") // 处理 POST /admin/employee/login
```

**`@RequestBody`** — 告诉 Spring「把请求体里的 JSON 反序列化成后面的这个对象」。前端 POST 时会带 `{"username":"xx","password":"xx"}`，Spring 靠它把 JSON 塞进 `EmployeeLoginDTO`。
```java
public Result<EmployeeLoginVO> login(@RequestBody EmployeeLoginDTO dto) {
    // 前端传来的 JSON 自动变成 dto 对象
}
```

**`@PathVariable`** — 把 URL 里 `{花括号}` 那一段取出来当参数。
```java
@PostMapping("/status/{status}")     // 如 /status/1
public Result startOrStop(@PathVariable Integer status, Long id)
// 1 自动填进 status 参数
```

**`@Autowired`** — 依赖注入：告诉 Spring「我要用这个对象，你给我把已经创建好的那个实例塞进来」，省去自己 `new`。背后的 IoC 原理见"进阶底层"。
```java
@Autowired
private EmployeeService employeeService;   // 我不用new，Spring给现成的
```

**`@Slf4j`**（Lombok）— 自动生成一个 `log` 日志对象，直接能用 `log.info(...)`。
```java
@Slf4j
public class EmployeeController {
    log.info("员工登录：{}", employeeLoginDTO);   // 不用自己写 Logger
}
```

**`@Api` / `@ApiOperation`** — 给接口文档工具看的"说明标签"，见第四部分。

---

**`@RestController` vs `@Controller` 处理流程对比（文字流程对比图）**

```
【@Controller 类】                        【@RestController 类】
请求 → Spring 找 handler                   请求 → Spring 找 handler
  → 方法返回【视图名/ModelAndView】           → 方法返回【Java对象】
  → 用视图解析器找同名 JSP/模板               → 自动调 @ResponseBody 做 JSON 转换
  → 渲染成【HTML页面】返回给浏览器             → 把 JSON 直接写回给浏览器
```

- 传统网站（返回 HTML 页面给浏览器看）用 `@Controller`。
- 前后端分离（前端要 JSON 数据自己渲染）用 `@RestController`。本项目的接口就是后者，全用 `@RestController`。两者本质差异就是**有没有 `@ResponseBody`（是否自动转 JSON）**。

**真实代码逐行注释**（`EmployeeController.login`）：

```java
@PostMapping("/login")                                    // 处理POST /admin/employee/login
@ApiOperation(value = "员工登录")                          // 文档里显示的接口说明
public Result<EmployeeLoginVO> login(@RequestBody EmployeeLoginDTO employeeLoginDTO) {
    // 参数：前端POST的JSON被@RequestBody转成employeeLoginDTO（装用户名密码）

    log.info("员工登录：{}", employeeLoginDTO);            // 打日志，方便排错

    Employee employee = employeeService.login(employeeLoginDTO); // 调Service去验证账号密码，返回数据库里的员工
    // ↑ 密码对不对？在不在？Service内部校验，校验失败会抛异常

    Map<String, Object> claims = new HashMap<>();         // 准备往JWT里塞的自定义数据
    claims.put(JwtClaimsConstant.EMP_ID, employee.getId()); // 把"登录者id"放进JWT

    String token = JwtUtil.createJWT(                       // 用工具类生成JWT令牌(登录凭证)
            jwtProperties.getAdminSecretKey(),              //   签名密钥
            jwtProperties.getAdminTtl(),                    //   过期时间
            claims);                                        //   携带的数据

    EmployeeLoginVO employeeLoginVO = EmployeeLoginVO.builder() // 用Lombok@Builder链式构造返回VO
            .id(employee.getId())
            .userName(employee.getUsername())
            .name(employee.getName())
            .token(token)                                    // 把令牌交给前端，以后请求带它
            .build();

    return Result.success(employeeLoginVO);                 // 包成统一结构返回
}
```

### 2.3 Service 层详解（重点：事务）

**职责**：真正的"业务大脑"。Controller 只负责收数据，真正「先查A，再判断，再写B，再改C」的逻辑都在 Service。

**`@Service`** — 标记"这是业务层组件"，交给 Spring 管理成一个 Bean（后面能被 Controller `@Autowired` 注进去）。
```java
@Service                     // 让Spring认识我是业务组件
public class OrderServiceImpl implements OrderService { }
```

**`@Transactional`** — **事务**注解，这是 Service 层最关键的一个。含义：**这个方法里所有数据库操作要么全部成功、要么全部回滚**（一个出错，前面全撤销，不留"半截数据"）。

**真实用在**：`OrderServiceImpl.submitOrder()`（下单方法）。看方法体就明白为什么必须加事务——它**一步里动了 3 张表**：
```java
@Transactional                                        // 事务：下面三件事绑一起
public OrderSubmitVO submitOrder(OrdersSubmitDTO ordersSubmitDTO) {
    orderMapper.insert(orders);           // ①往订单表插入1条
    orderDetailMapper.insertBatch(...);   // ②往订单明细表插入N条
    shoppingCartMapper.deleteByUserId(userId); // ③清空购物车
}
```
**如果去掉 `@Transactional` 会出什么问题**：假设②往明细表插到第 3 条时数据库突然出错，②报异常了，但①的订单已经写进库了、③还没执行——结果就是**库里多了一条"孤零零的订单"，却没有对应的明细**，用户明明下单失败，数据却坏了。加上事务后，②一出错，①、②全部回滚，库保持干净。

（`@Transactional` 原理 = 代理，见"进阶底层"。`SkyApplication` 上还标了 `@EnableTransactionManagement` 开启注解事务管理。`DishServiceImpl`、`SetmealServiceImpl` 里同时操作"主表+关联表"的方法也加了事务，道理相同。附带一提：下单前那些"地址为空、购物车为空就抛异常"是**业务校验**，靠后面全局异常处理器兜住。）

### 2.4 Mapper 层详解

**职责**：唯一直接碰 SQL 的层。它把"Java 方法调用"翻译成"数据库 SQL"。

**接口 + `@Mapper`** — `EmployeeMapper` 是个**接口**（没有实现类！），`@Mapper` 让 MyBatis 启动时给这个接口生成一个"动态代理实现"，你不用写实现类。
```java
@Mapper                      // MyBatis给这个接口自动生成实现
public interface EmployeeMapper {
    Employee getByUsername(String username);
}
```

**简单 SQL 用注解直接写**（`@Select`/`@Insert`/`@Update`/`@Delete`）：
```java
@Select("select * from employee where username = #{username}")
Employee getByUsername(String username);   // #{username}是占位符，自动安全地填参数
```

**复杂/动态 SQL 用 XML 文件**，比如 `pageQuery`（要不要 `where name like` 得看传没传 name）。本项目分工：**简单固定的 SQL 用注解，需要拼接/判断的用 XML**。

**XML 位置和配置**：
- XML 放在：`sky-server/src/main/resources/mapper/` 下，如 `EmployeeMapper.xml`，一个 Mapper 一个。
- 扫描配置在 `application.yml`：
```yaml
mybatis:
  mapper-locations: classpath:mapper/*.xml   # classpath=编译后的resources目录；*匹配该目录所有xml
```
XML 通过 `namespace="com.sky.mapper.EmployeeMapper"` + `<select id="pageQuery">` 来**和 Java 接口方法一一绑定**（namespace=接口全限定名，id=方法名）：
```xml
<mapper namespace="com.sky.mapper.EmployeeMapper">  <!-- 对应哪个接口 -->
  <select id="pageQuery" resultType="com.sky.entity.Employee">  <!-- 对应哪个方法 -->
    select * from employee
    <where>
      <if test="name != null and name != ''">   <!-- 动态：有name才拼这行 -->
        and name like concat('%',#{name},'%')    <!-- 模糊查询 -->
      </if>
    </where>
  </select>
</mapper>
```

**`@AutoFill`** 也标在 Mapper 方法上（`insert`、`update`），见第三部分。

### 2.5 POJO 层 + Lombok

entity/dto/vo 里的类**几乎不写逻辑**，就是字段 + getter/setter。全用 Lombok 注解偷懒。

**`@Data`** — 一个顶好几个：帮你生成**所有字段的 getter、setter**，以及 `toString/equals/hashCode`。
```java
@Data                      // 下面每个字段的get/set方法编译器阶段自动生成
public class Employee implements Serializable {
    private Long id;       // 你只写字段
    private String name;
    // 不需要手写 getId()/setId()，@Data帮你生成
}
```

**`@Builder`** — 生成"链式构建器"，方便创建对象（`.id(...).name(...).build()` 靠它）。
```java
@Builder
public class Employee {...}
// Employee.builder().id(1L).name("张三").build();  链式写法
```

**`@NoArgsConstructor` / `@AllArgsConstructor`** — 生成无参构造 / 全参构造。

**`@Data` 生成 getter/setter "运行时怎么起作用"（概念，不涉源码）**：
Lombok **不是运行时魔法，它发生在编译期**。Lombok 挂接进 javac 编译过程，在 `Employee.java` 变成 `.class` 之前，看到类上有 `@Data`，就**自动往源码里补齐了 getter/setter 的字节码**。所以编译出的 `.class` 里本来就有这些方法，JVM 运行时**根本不知道有 Lombok**——它只当这是一份"手写了全套 getter/setter 的普通类"。Spring、Jackson、MyBatis 正常调 `employee.getName()`、`setId(x)`，毫无障碍。结论：**Lombok 是"编译期偷懒工具"，省的是敲键盘的功夫，产出的还是普通 Java 类**。

## 三、进阶特性：AOP + 自定义注解 @AutoFill（最核心）

### 3.1 AOP 是什么？——"后厨的切菜师傅"

餐馆里每天都有"切菜"动作——切土豆要洗、切肉要洗、切葱要洗，**每个做菜师傅在动刀前都重复做同一件事**。如果让每个师傅自己记着"我切之前得先洗手"，总有人忘。

AOP 的做法：**单独雇一个"切菜前检查师傅"**，规定好"只要有人要动刀（切入点），他必须先拦下来检查洗手（增强逻辑）"。做菜师傅们彻底不用管了。

对应到代码：
- **后厨师傅** = 业务方法（`mapper.insert(...)`、`mapper.update(...)`）
- **"只要动刀"这个规则** = **切入点（Pointcut）**：声明"我关心哪些方法"
- **"检查洗手"这段逻辑** = **通知（Advice）/增强**：真正执行前要额外做的事
- **拦下来的检查师傅** = **切面（Aspect）** = 一个"规则+逻辑"打包的类

**解决的核心痛点**：把"**很多方法都要重复做的横切逻辑**"抽出来写一次，业务方法干干净净。项目里大量 Mapper 方法都要"插入/更新前自动填 createTime、createUser"，这正是典型的横切逻辑，于是项目用 AOP 一刀切搞定，不用在每个 Mapper 方法里手动写。

### 3.2 为什么需要 @AutoFill？解决什么痛点？

没有它之前每次 insert 得手动写（重复且易漏）：
```java
employee.setCreateTime(LocalDateTime.now());  // 每次都得写！
employee.setCreateUser(currentLoginId);       // 每次都得写！
employee.setUpdateTime(LocalDateTime.now());
employee.setUpdateUser(currentLoginId);
```
而数据库表里 create_time/create_user/update_time/update_user 这**4 个"公共字段"几乎所有表都有**，意味着"新增"要写 4 行、"修改"要写 2 行，几十个方法 × 每个业务 = 到处重复、极易忘。

**痛点**：① 重复代码爆炸；② 容易漏填（漏了就 NULL）；③ 一旦改规则得改几十处。

**@AutoFill 的思路**：给 `insert`/`update` 方法贴个"标签"，让 AOP 切面在方法真正执行**前**自动把公共字段填好。业务代码零侵入，告别重复。

### 3.3 三个文件的真实代码逐行拆解

**① `AutoFill.java` —— 自定义"标签"**（sky-server/.../annotation/AutoFill.java）
```java
@Target(ElementType.METHOD)          // 这个标签只能贴在【方法】上
@Retention(RetentionPolicy.RUNTIME)  // 标签要保留到运行时，AOP才能读到它
public @interface AutoFill {         // 定义一个注解（用@interface）
    OperationType value();           // 注解可以带"参数"，这里是数据库操作类型(INSERT/UPDATE)
}
```
- `@interface AutoFill`：定义注解就是用 `@interface` 关键字。
- `@Target(ElementType.METHOD)`：限定贴哪儿（贴方法上）。
- `@Retention(RetentionPolicy.RUNTIME)`：存活期到运行时，AOP 才能通过反射读它（SOURCE/CLASS 都取不到）。
- `OperationType value()`：注解"参数"，`@AutoFill(value = OperationType.INSERT)` 告诉切面是插入还是更新。

**② `AutoFillConstant.java` —— 常量仓库**（sky-common/.../constant/AutoFillConstant.java）
```java
public class AutoFillConstant {
    public static final String SET_CREATE_TIME = "setCreateTime";
    public static final String SET_UPDATE_TIME = "setUpdateTime";
    public static final String SET_CREATE_USER = "setCreateUser";
    public static final String SET_UPDATE_USER = "setUpdateUser";
}
```
把 4 个 setter 名字符串抽成常量，避免切面里手打字符串打错。纯工具类，避免魔法字符串。

**③ `AutoFillAspect.java` —— 切面（核心逻辑）**（sky-server/.../aspect/AutoFillAspect.java）
```java
@Aspect                          // 声明：这是一个AOP切面
@Component                       // 让Spring管理它
@Slf4j
public class AutoFillAspect {

    // 【切入点】规定"关心哪些方法"：com.sky.mapper包下、且贴了@AutoFill的方法
    @Pointcut("execution(* com.sky.mapper.*.*(..)) && @annotation(com.sky.annotation.AutoFill)")
    public void autoFillPointCut(){}

    // 【前置通知】在这些方法真正执行【之前】干这件事
    @Before("autoFillPointCut()")
    public void autoFill(JoinPoint joinPoint){
        // 1.拿到当前被拦截方法上的 @AutoFill，读它的value(INSERT还是UPDATE)
        MethodSignature signature = (MethodSignature) joinPoint.getSignature();
        AutoFill autoFill = signature.getMethod().getAnnotation(AutoFill.class);
        OperationType operationType = autoFill.value();

        // 2.拿到方法的第一个参数 —— 那个实体对象(Employee等)
        Object[] args = joinPoint.getArgs();
        if(args == null || args.length == 0){ return; }   // 没参数就没法填，直接返回
        Object entity = args[0];                          // 第一个参数就是要被填充的实体

        // 3.准备要填进去的数据
        LocalDateTime now = LocalDateTime.now();          // 当前时间
        Long currentId = BaseContext.getCurrentId();      // 当前登录用户id（从ThreadLocal取）

        // 4.根据操作类型，用【反射】调用实体的setter来赋值
        if(operationType == OperationType.INSERT){
            Method setCreateTime = entity.getClass().getDeclaredMethod("setCreateTime", LocalDateTime.class);
            Method setCreateUser = entity.getClass().getDeclaredMethod("setCreateUser", Long.class);
            Method setUpdateTime = entity.getClass().getDeclaredMethod("setUpdateTime", LocalDateTime.class);
            Method setUpdateUser = entity.getClass().getDeclaredMethod("setUpdateUser", Long.class);
            setCreateTime.invoke(entity, now);
            setCreateUser.invoke(entity, currentId);
            setUpdateTime.invoke(entity, now);
            setUpdateUser.invoke(entity, currentId);      // 插入填4个字段
        } else if(operationType == OperationType.UPDATE){
            // 更新只填 updateTime、updateUser 两个字段
            ...
        }
    }
}
```
- `@Pointcut("execution(* com.sky.mapper.*.*(..)) && @annotation(...)")`：`*` 返回类型任意，`com.sky.mapper.*.*` 包下所有类所有方法，`(..)` 参数任意；再 `&&` "且方法上贴了 `@AutoFill`"。整体 = **"mapper包下所有贴了@AutoFill的方法"**。
- `joinPoint` = **连接点**，像"被拦截方法现场的遥控器"，能拿到方法签名、参数、被调对象。
- **反射**：`entity.getClass().getDeclaredMethod("方法名", 参数类型)` 在**运行时**动态拿到方法对象，再 `.invoke(对象, 参数)` 调用。切面不知道 entity 具体是 Employee 还是 Category——但没关系，反射让"用字符串方法名 + 运行时对象"就能调 setter，这就是切面能"万能处理所有实体"的原因。

### 3.4 完整时间线：员工登录 → 记录 createUser 一路打通到 AOP

场景：管理员登录后，新增一个员工，该员工的 create_user 记下是哪个管理员加的。

- **第 1 步**｜管理员先登录：POST `/admin/employee/login` → `EmployeeController.login()` 校验通过，用 `employee.getId()` 生成 JWT token 返回前端。
- **第 2 步**｜前端拿 token 再调"新增员工"：POST `/admin/employee`，请求头带 `token: xxx`。
- **第 3 步**｜请求先经拦截器 `JwtTokenAdminInterceptor.preHandle()`（Spring MVC 进 Controller **之前**先过拦截器）：
  ```java
  String token = request.getHeader("token");        // 取出请求头里的token
  Claims claims = JwtUtil.parseJWT(secretKey, token); // 解析验证
  Long empId = Long.valueOf(claims.get("empId").toString()); // 从token里拿出登录者id
  BaseContext.setCurrentId(empId);   // ★把id存进ThreadLocal
  return true;                       // 放行
  ```
- **第 4 步**｜到达 `EmployeeController.save(@RequestBody EmployeeDTO)` → 调 `employeeService.save(dto)`。
- **第 5 步**｜Service 把 `EmployeeDTO` 复制成 `Employee entity`，调 `employeeMapper.insert(entity)`。
- **第 6 步｜AOP 切面介入！**：因为 `EmployeeMapper.insert` 贴了 `@AutoFill(value = OperationType.INSERT)`，且位于 `com.sky.mapper` 包，命中切入点。所以在 MyBatis 真正执行 insert SQL **之前**，Spring 先执行 `AutoFillAspect.autoFill(joinPoint)`：
  - 拿 `@AutoFill` → operationType = INSERT；
  - 拿第一个参数 = `entity`（Employee 对象）；
  - `BaseContext.getCurrentId()` → 取第 3 步存进去的 empId；
  - 反射调 `entity.setCreateUser(empId)`、`setCreateTime(now)`…… **此刻 createUser 才被填上**。
- **第 7 步**｜切面执行完，控制权交回，真正的 insert SQL 才执行——把**已填好 create_user/create_time** 的 entity 写进数据库。
- **第 8 步**｜返回 Result。整条链路 Service 和 Mapper **一行填 createUser 的代码都没写**，全靠标签 + 切面。

> **为什么能跨方法、跨类把第3步存的 id 用到第6步？** 靠 `BaseContext` 里的 `ThreadLocal`。同一 HTTP 请求从进来到响应结束，全程跑在**同一个线程**上。`ThreadLocal` 相当于"每个线程私有的小抽屉"，第 3 步 `set` 放进去、第 6 步（同线程）`get` 取出来。不同用户=不同线程=抽屉互不干扰。

> ⚠️ **本项目的一个真实隐患（我核对过源码）**：两个 JWT 拦截器（`JwtTokenAdminInterceptor` / `JwtTokenUserInterceptor`）都只 `setCurrentId`，**没有在 `afterCompletion` 里 `remove()`**。Tomcat 用线程池，线程会被复用 —— 上一个请求残留的 userId 一旦被"没走拦截器"的请求（放行路径、支付回调、异步任务）读到，就会拿到**上一个人的 id**，导致自动填充的 `update_user` 记错人（🔇 静默错误，不报错但数据是错的）。
> **修法**：拦截器里实现 `afterCompletion`，调用 `BaseContext.removeCurrentId()`。详见 `苍穹外卖面试手册.md` 坑 P1-1。

### 3.5 底层原理单独拆（反射 / 代理 / IoC）

**① IoC（控制反转）**：以前想用一个类得自己 `new` 并管理依赖。IoC 把"创建和给谁用"的权力反转交给 Spring 容器。你标 `@Component`/`@Service`/`@Controller`，Spring 启动时把类创建成 Bean 放进"大仓库"（容器）。谁想用写 `@Autowired`，Spring 自动从仓库塞给你。`EmployeeController` 里的 `employeeService` 就是容器塞的，**全程没有一个 `new`**。

**② 代理（Proxy）—— `@Transactional`、`@AutoFill` 的底层共同根基**：Spring 不会直接调你的 `insert()` 或 `submitOrder()`，而是先创建**代理对象**（披着你类外衣、能"插入额外动作"的替身），调用走代理。对事务：代理在方法前 `begin`、成功 `commit`、异常 `rollback`；对 AOP：代理在执行方法前/后调切面逻辑（`@Before` = 执行前插入）。`@AutoFill`、`@Transactional` 之所以"凭空生效"，就是因为 Spring 用代理把它们翻译成"方法前/后插入的代码"。

**③ 反射（Reflection）**：普通代码编译时定死调哪个方法（`employee.setCreateUser(x)` 写死）。反射让你**运行时**才决定"这个实体有没有一个叫 `setCreateUser`、参数是 `Long` 的方法？有就调"。所以同一切面不改代码，处理 Employee/Category/Orders 都行——因为不写死类名，而是靠反射去"问"每个实体。

> 三者关系总结：**Spring 靠 IoC 管对象，靠代理把切面/事务织进方法，切面内部再用反射去操作"运行时才知道的具体实体"**。

## 五、额外扫盲

### 5.1 `@SpringBootApplication` 包含哪三个注解？启动时干嘛？

它出现在 `SkyApplication.java`。是组合注解，等于下面三个叠加：
1. **`@SpringBootConfiguration`** —— 标记这是配置类。
2. **`@EnableAutoConfiguration`** —— **自动配置开关**。根据 classpath 引入了哪些 jar（Redis、MyBatis、Druid），Spring 自动建好对应配置对象。所以只要引入依赖 + 写 yml，数据库连接就能用。
3. **`@ComponentScan`** —— **组件扫描**。默认扫它所在类（SkyApplication）所在包 `com.sky` 及其所有子包，把标了 `@Component/@Service/@Controller/@Repository` 的类注册成 Bean。这就是为什么所有类都在 `com.sky.xxx` 下——放错包就扫不到，`@Autowired` 直接报错。

**启动时做了什么**：`SpringApplication.run(...)` 触发：启动内嵌 Tomcat → @ComponentScan 把所有 Bean 放进容器 → @EnableAutoConfiguration 自动配好数据库/Redis → 读 application.yml → 开启 @EnableTransactionManagement 等开关 → 就绪后监听 8080。`SkyApplication` 类上还标了 `@EnableTransactionManagement`（事务）、`@EnableCaching`（缓存）、`@EnableScheduling`（定时任务）、`@Slf4j`（日志）。

### 5.2 application.yml 关键配置逐项解释

数据库（application.yml 通过 `spring.profiles.active: dev` 激活 dev 配置；`${sky.datasource.host}` 是**占位符**，引用 `sky.datasource.host` 的值，把"要改的"集中一处）：
```yaml
server:
  port: 8080            # 后端启动后监听的端口
spring:
  profiles: { active: dev }   # 激活名为dev的配置文件(application-dev.yml)
  datasource:            # 数据库连接配置
    druid:               # 用阿里Druid连接池
      driver-class-name: com.mysql.cj.jdbc.Driver  # MySQL驱动类(告诉程序用哪个数据库驱动)
      url: jdbc:mysql://localhost:3306/sky_take_out?serverTimezone=Asia/Shanghai&...  # 连哪个库(时区/编码)
      username: root     # 数据库账号
      password: root     # 数据库密码
  redis:                 # Redis缓存(存token/缓存菜品/购物车等)
    host/port/password/database: ...
```
`application-dev.yml` 里 `sky.datasource.host: localhost`、`database: sky_take_out`、`password: root` 是真正被占位符替换的值。合起来 = **程序要连 localhost:3306 上名叫 sky_take_out 的 MySQL，账号 root**。

MyBatis：
```yaml
mybatis:
  mapper-locations: classpath:mapper/*.xml   # 加载XML映射文件(前面讲过)
  type-aliases-package: com.sky.entity        # 给实体类起别名，XML里写Employee不用写全路径
  configuration: { map-underscore-to-camel-case: true } # 数据库下划线 → Java驼峰(create_time→createTime)
```

日志：`logging.level.com.sky.mapper: debug` = 打印 SQL，控制台看 MyBatis 实际执行的语句。

JWT（`sky.jwt`）：
```yaml
sky: jwt:
  admin-secret-key: itcast    # 签发JWT用的签名密钥(防篡改)
```

## 6.1 JWT 登录鉴权全链路（后端完整闭环）

**它解决什么问题？** HTTP 是无状态的：同一个用户发两个请求，服务器根本不记得"你是谁"。JWT（JSON Web Token）就是一个"能自己证明身份"的通行证——服务器把它发给前端，前端每次请求带上它，服务器一验签名就知道"这是谁发的、有没有过期"。关键是：**验证不需要查数据库**，纯靠数学签名。

**JWT 由三段拼成**（用 `.` 分隔）：`xxx.yyy.zzz`
- `xxx` header：声明用什么算法（HS256）。
- `yyy` payload：你要带的数据（这里就是 `empId`/`userId`）+ 过期时间。
- `zzz` signature：用**服务端秘钥**把前两段算出来的签名——**只有持有秘钥的服务器能造/验**，所以别人改不了内容，改了签名就对不上。

**闭环第一步：登录成功→签发**（`EmployeeController.login`，前面已逐行注释）。核心是 `JwtUtil.createJWT(secretKey, ttl, claims)`：
```java
String token = JwtUtil.createJWT(
        jwtProperties.getAdminSecretKey(),  // 签名秘钥(和校验时用同一个)
        jwtProperties.getAdminTtl(),        // 过期时间(毫秒)，yml里是7200000=2小时
        claims);                            // 塞进去的数据，如 empId
```
`JwtUtil.createJWT` 内部（我读过）用 `Jwts.builder().setClaims(claims).signWith(HS256, 秘钥).setExpiration(过期时间)` 拼出三段 token 返回。然后把 token 放进 `EmployeeLoginVO` 交回给前端。

**闭环第二步：前端每次请求带上**——前端拿到 token 后，之后每个需要登录的请求，都在**请求头**里带一个字段（管理端叫 `token`，用户端叫 `authentication`，见 yml 的 `admin-token-name` / `user-token-name`）。

**闭环第三步：请求进来先过拦截器校验**（`JwtTokenAdminInterceptor.preHandle`）：
```java
String token = request.getHeader("token");   // ①从请求头取token
Claims claims = JwtUtil.parseJWT(secretKey, token); // ②验签+解析(秘钥不对/过期都抛异常)
Long empId = Long.valueOf(claims.get("empId").toString()); // ③取出登录者id
BaseContext.setCurrentId(empId);             // ④存进ThreadLocal，供本次请求后续使用
return true;                                  // ⑤验过就放行
```
若解析抛异常（签名被改/过期/根本没带），就 `response.setStatus(401)` 并 `return false`——请求被拦下，进不了 Controller。

**闭环第四步：哪些路径要拦？** 在 `WebMvcConfiguration.addInterceptors` 里注册拦截器并指定拦截范围：
```java
registry.addInterceptor(jwtTokenAdminInterceptor)
        .addPathPatterns("/admin/**")          // 管理端所有路径都要登录
        .excludePathPatterns("/admin/employee/login"); // 但登录接口本身不能拦(否则没法登录)
```
逻辑：`/admin/**` 全拦，唯独放行登录接口（登录时还没 token）。用户端同理，还放行了 `user/shop/status`（查店铺营业状态不用登录）。

> **一句话记整个鉴权闭环**：登录签发 → 前端存好每次带 → 拦截器验签放行并把 id 塞进 ThreadLocal → 业务层随时能拿到"当前是谁"。管理端和用户端是**两套独立的秘钥 + 两个 token 字段名 + 两个拦截器**，互不通用。

## 6.2 @Transactional 会"失效"的 5 大坑（进阶必知）

注解本身生效依赖"代理"。只要**这个调用没走代理**，`@Transactional` 就静悄悄失效——你以为有事务，其实没有。最常见 5 种：

**坑1：同类内部方法自己调自己（最常见）**
```java
@Transactional
public void orderA(){ orderMapper.insertA(); this.orderB(); } // 调同类方法
@Transactional
public void orderB(){ orderMapper.insertB(); }   // B其实没走代理!
```
原因：Spring 的代理是"**从外面调这个 Bean 时才生效**"。`this.orderB()` 是对象内部直接调用自己，**没经过代理**，所以 orderB 上的事务注解被无视。解决办法：把 B 拆到另一个 Service，或用 `@Autowired` 注入自身代理再调。

**坑2：方法不是 public**
Spring 的 JDK 动态代理/注解扫描默认只处理 public 方法。private 方法上的 `@Transactional` 不生效（因为代理没法拦截 private）。

**坑3：异常被自己 catch 吞掉**
```java
@Transactional
public void save(){
    try { mapper.insertA(); } catch(Exception e){ }  // 异常被吞了!
    mapper.insertB(); // 若B失败，A已经入库不会回滚
}
```
事务回滚靠"异常冒泡出方法"。你 catch 住不抛，Spring 就以为一切正常，不会回滚。要么别吞，要么 catch 后 `throw new RuntimeException(...)`。

**坑4：抛的是"检查异常"(checked Exception)默认不回滚**
Spring 默认**只对运行时异常 `RuntimeException` 回滚**。若方法 `throws Exception`（检查异常），默认不触发回滚。要处理可在注解写 `@Transactional(rollbackFor = Exception.class)`。你项目里业务异常都继承 `RuntimeException`，所以默认能回滚。

**坑5：在 `@Async` / 新起线程里执行**
事务上下文**不跨线程**。方法标了 `@Transactional`，但如果被丢进线程池（`@Async`、`CompletableFuture`、自己 new Thread）执行，新线程里没有事务绑定，注解等于没写。
（补充一个容易配错的点：`propagation = REQUIRES_NEW` 会**挂起外层事务、另开一个事务并多占一个连接**，在外层已持锁时容易"自己等自己"。默认 `REQUIRED` 就够用，别乱改。）

> 对照你项目：`OrderServiceImpl.submitOrder` 是**从 Controller 外部进来调**的 public 方法、异常是 `AddressBookBusinessException`（继承 RuntimeException，会自动冒泡）→ 所以事务能正常生效。

## 6.3 MyBatis 深入：`#{}` vs `${}`、动态 SQL、批量插入、主键回填

### `#{name}` 与 `${name}` 的区别（最重要，直接决定安全性）

用你 `EmployeeMapper.xml` 的 update 片段解释：
```xml
<if test="name != null"> name = #{name}, </if>
```
- **`#{}` = 预编译占位符**：MyBatis 会把它翻译成 SQL 里的 `?`，再用参数去填充。相当于"先把 SQL 骨架发给数据库用 PrepareStatement 编译，再把值安全地绑定上去"。**能防 SQL 注入**，几乎永远用它。
- **`${}` = 直接字符串拼接**：把值原样拼进 SQL 字符串。比如 name 传 `1; drop table user` 就会直接拼进去执行——**极其危险**。什么时候才用？拼接"动态的表名/列名/排序字段"这些**不能当参数**的地方（如 `order by ${sortColumn}`），因为列名不能是 `?` 占位。**传值永远用 `#{}`**。

### 动态 SQL 三兄弟（你 OrderMapper.xml 里全有）

**`<where>`**：自动处理"要不要 where"和"多余的 and"。
```xml
<select id="pageQuery" resultType="Orders">
  select * from orders
  <where>                            <!-- 若里面一个if都不满足，连where都不生成 -->
    <if test="number != null and number!=''"> and number like concat('%',#{number},'%') </if>
    <if test="status != null"> and status = #{status} </if>
  </where>
  order by order_time desc
</select>
```
`<where>` 会帮你去掉第一个条件前面多余的 `and`。这就是为什么分页查询能"按需拼接条件"，一个方法适配多种查询。

**`<if test="...">`**：条件成立才拼这段 SQL。test 里写的是 **Java/OGNL 表达式**（`!=`、`==`、`and`、`or`、`!= ''`）。注意 XML 里 `>`、`<` 要写成 `&gt;`、`&lt;`（看上面 `order_time &gt;= #{beginTime}`）。

**`<set>`**：专用于 update，自动处理末尾多余的逗号。见 `OrderMapper.xml` 的 update——因为只改了某些字段，`<set>` 加 `<if>` 就能做到"只更新非空字段"的动态 update（这也正是 `@AutoFill` 只填了 update_time/update_user 两个之后、其余靠这套拼接的原因）。

**`<foreach>`**：批量处理集合。你的下单里 `insertBatch` 就是这么把购物车列表一次性插进去的（`OrderDetailMapper.xml`）：
```xml
<insert id="insertBatch">
  insert into order_detail (name, image, order_id, ...) values
  <foreach collection="orderDetailList" item="od" separator=",">
    (#{od.name},#{od.image},#{od.orderId},...)
  </foreach>
</insert>
```
- `collection` = 方法传进来的参数名（集合）；`item` = 循环里每个元素的临时名；`separator=","` = 每轮之间用逗号隔开。效果：一条 insert 插 N 行，比循环调 N 次 insert 高效得多。

### 主键回填 useGeneratedKeys
`OrderMapper.xml` 的 insert 有这俩属性：
```xml
<insert id="insert" useGeneratedKeys="true" keyProperty="id">
```
含义：**插入后，把数据库自增生成的 id 自动填回 Java 对象的 `id` 字段**。为什么必须？看 `submitOrder`：
```java
orderMapper.insert(orders);          // 插完，orders.getId()此时已有值
orderDetail.setOrderId(orders.getId()); // 明细要拿这个订单id去关联！
```
没有回填，`orders.getId()` 还是 null，明细就关联不上主订单了。

## 6.4 全局异常 + 业务异常体系（"该抛什么、谁来接"）

### 为什么要单独搞一套异常？
如果每个 Service 都自己 try-catch 再返回个错误码，代码会写吐、还不统一。思路是：**业务层"放心大胆地 throw"，由全局唯一的异常处理器统一"接住并转成前端能看的 JSON"**。

### 两层异常结构（都在 sky-common/exception/）
```java
// 基类：所有业务异常的爸爸
public class BaseException extends RuntimeException {
    public BaseException(String msg){ super(msg); }
}
// 子类：具体场景。如 账号不存在/密码错/地址簿为空/订单状态错...
public class AddressBookBusinessException extends BaseException {
    public AddressBookBusinessException(String msg){ super(msg); }
}
```
十几个 `XxxException` 全继承 `BaseException`。好处：业务层只要 `throw new AddressBookBusinessException("地址为空")`，上层只用 catch 基类一种即可。看 `submitOrder` 真实抛法：
```java
if(addressBook == null){
    throw new AddressBookBusinessException(MessageConstant.ADDRESS_BOOK_IS_NULL);
}
```
`MessageConstant` 里存错误文案常量，避免到处手打字符串。

### 谁来接？`GlobalExceptionHandler`（sky-server/handler/）
```java
@RestControllerAdvice   // 全局"旁听生"：任何Controller方法抛异常它都来兜底
public class GlobalExceptionHandler {
    @ExceptionHandler(BaseException.class)      // 只接BaseException及其子类
    public Result exceptionHandler(BaseException ex){
        return Result.error(ex.getMessage());   // 转成前端可读的错误JSON
    }
    @ExceptionHandler(SQLIntegrityConstraintViolationException.class) // 接数据库唯一键冲突
    public Result exceptionHandler(SQLIntegrityConstraintViolationException ex){
        if(message.contains("Duplicate entry")){ ... return Result.error(username+"已存在"); }
    }
}
```
- `@RestControllerAdvice` = `@ControllerAdvice` + `@ResponseBody`，让所有 Controller 的错误都流到这儿统一返回 JSON，不用每个接口自己 try-catch。
- `@ExceptionHandler(某异常.class)`：**按异常类型精准接**。方法里写 `ex.getMessage()`，把业务层塞的文案原样返回给前端（如"该账号已存在"）。

> 一句话：**业务层只负责 throw（把"为什么不行"写进 message），控制器层靠 @RestControllerAdvice 一把全接住转成 Result.error 给前端**。前端拿到 code=0 + msg 就能弹提示。

## 6.5 Redis 缓存 + 定时任务 + WebSocket（代码里的三块"看不见的功能"）

### (A) Redis 缓存 —— `@Cacheable` / `@CacheEvict`
`@EnableCaching` 开启缓存注解功能（SkyApplication 上有）。项目典型用法在**套餐查询**（user 端 `SetmealController.list`）：
```java
@Cacheable(cacheNames = "setmealCache", key = "#categoryId") // 缓存名::key => setmealCache::100
public Result<List<Setmeal>> list(Long categoryId) { ... }
```
- `@Cacheable` = **"先查缓存，命中就直接返回，不执行方法；没命中才执行方法并把结果存进缓存"**。key 按分类 id 存，所以同一个分类下次直接走缓存，省一次数据库查询（高并发下的菜单浏览很吃香）。
- 代价：**数据变了缓存要删**。所以管理端改套餐时用 `@CacheEvict` 清缓存（`admin/SetmealController`）：
```java
@CacheEvict(cacheNames = "setmealCache", allEntries = true) // 全删这套缓存，下次重新查库
```
- `RedisConfiguration` 里配了个 `RedisTemplate`，`setKeySerializer(new StringRedisSerializer())` 是保证 key 用字符串存，避免乱码。也可用它直接 `redisTemplate.opsForValue().set/get` 手动读写缓存。
  > ⚠️ **注意：只配了 key，没配 value**。value 仍走默认的 **JDK 序列化** → 存对象是二进制乱码、`redis-cli` 看不懂、类还必须实现 `Serializable`。改进：value 用 `GenericJackson2JsonRedisSerializer`，或直接用 `StringRedisTemplate` 手动 JSON（**黑马点评里就是这么做的**，也是那一课真实踩过的坑）。详见面试手册坑 P1-2。
- 思考题：为什么缓存的是"查多改少"的数据？（套餐/菜品用户看的多，改的少——缓存才划算。）

### (B) 定时任务 —— `@EnableScheduling` + `@Scheduled`
处理那些"该在某个时间点自动做、但没人会去点按钮"的事。`OrderTask` 两个任务：
```java
@Scheduled(cron = "0 * * * * ? ")   // cron表达式：每分钟(秒=0)触发一次
public void processTimeoutOrder(){   // 找出"待付款超过15分钟"的订单，自动取消
    LocalDateTime time = LocalDateTime.now().plusMinutes(-15); // 15分钟前的时刻
    List<Orders> list = orderMapper.getByStatusAndOrderTimeLT(Orders.PENDING_PAYMENT, time);
    for(Orders o : list){ o.setStatus(Orders.CANCELLED); o.setCancelReason("订单超时，自动取消"); orderMapper.update(o); }
}

@Scheduled(cron = "0 0 1 * * ?")     // 每天凌晨1点
public void processDeliveryOrder(){  // 把"派送中超过1小时"的订单自动设为已完成 }
```
- **cron 表达式** = 定时规则字符串，6~7 段依次是 `秒 分 时 日 月 周`。`0 * * * * ?` = 每分整点触发；`0 0 1 * * ?` = 每天 1 点。不会写先记"从左到右是秒分时日月周"，`?` 表示"不指定"（通常用在周/日位置）。
- 这不就是"没人碰订单、到点自动改状态"吗？它和 @Transactional 协同：这些 update 改了状态入库。

### (C) WebSocket —— 服务端"主动"推消息给浏览器
HTTP 是"前端问、后端答"（单向）。WebSocket 是一条**一直保持的长连接**，让**服务器能主动给客户端发消息**——正好用来做"新订单来的时候，管理端网页不刷新也能弹提示"。

`WebSocketServer`（@ServerEndpoint("/ws/{sid}")）维护一个 `Map<sid, Session>` 存所有在线连接：
- `@OnOpen`：客户端连上时把 session 存进 map；
- `@OnClose`：断开时移除；
- `sendToAllClient(msg)`：**给所有在线的客户端广播消息**（遍历 sessionMap 逐个 sendText）。

真实触发点，看 `OrderServiceImpl` 两处：
```java
// 用户支付成功后 (type=1 来单提醒)
Map map = new HashMap();
map.put("type",1); map.put("orderId", ordersDB.getId()); map.put("content","订单号："+outTradeNo);
webSocketServer.sendToAllClient(JSON.toJSONString(map));   // 推给所有在线的管理端浏览器

// 用户催单 (type=2)
map.put("type",2); ...
```
所以流程是：**用户付钱 → paySuccess 改状态 → 通过 WebSocket 广播"type:1 新订单" → 管理端浏览器收到消息弹出"新订单来了"**。这就是"前后端分离下服务器主动推送"的实现。`WebSocketTask` 那个每5秒广播的是演示用例（被注释掉了），真实用在上面的订单提醒。

## 6.6 订单状态机（把业务复杂度串起来）

先看 `Orders` 实体里定义的状态常量（这就是"状态机"的各个状态）：
```java
// 订单状态
public static final Integer PENDING_PAYMENT = 1;   // 待付款
public static final Integer TO_BE_CONFIRMED = 2;   // 待接单
public static final Integer CONFIRMED = 3;         // 已接单
public static final Integer DELIVERY_IN_PROGRESS = 4; // 派送中
public static final Integer COMPLETED = 5;         // 已完成
public static final Integer CANCELLED = 6;         // 已取消
// 支付状态
public static final Integer UN_PAID = 0;  // 未支付
public static final Integer PAID = 1;     // 已支付
public static final Integer REFUND = 2;   // 退款
```
**"状态机" = 规定状态怎么按顺序流转、谁负责推进。** 结合前面看每个状态由谁触发：

```
[下单 submitOrder]   → status=1 待付款, payStatus=0
[支付 paySuccess]     → status=2 待接单, payStatus=1 (WebSocket提醒管理端type=1)
[商家接单]            → status=3 已接单
[商家派送]            → status=4 派送中
[送达/定时任务]       → status=5 已完成
[超时/取消/拒单]      → status=6 已取消 (定时任务/用户退单/商家拒单)
```
几个对照真实代码的细节：
- **"状态数字"不能乱跳**：比如用户没支付就不能接单，代码里每个推进状态的方法都会先 `orderMapper.getById` 查当前状态再判断。这也是为什么 6.5(B) 的定时任务要找"待付款超15分钟"的（status=1）而不是所有单——避免误伤已完成/已取消的单。
- **每个状态变更基本都会 update 对应的附加字段**：取消要填 `cancelReason`+`cancelTime`，拒单要填 `rejectionReason`，送达要填 `deliveryTime`。这些在 `OrderMapper.xml` 那个 `<set>`+`<if>` 动态 update 里按需拼接。
- **为什么要用"状态常量"而不是直接写 `1`/`5`？** 可读性 + 防手滑。`Orders.PAID` 比裸写 `1` 清楚得多，改一处全生效。

> **状态机对你最大的价值**：看懂它，你就看懂了一个"复杂业务 Service"是怎么被拆成"若干小方法、每个只推进一个状态"的。面试被问"你这个下单流程怎么设计的"，就是把这个流转图讲出来。
