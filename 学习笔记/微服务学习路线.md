## 3. MQ 的学习决策（2026.09.26 修订：**改为全量跟完**）

> **你的判断**：黑马 MQ 讲得好，直接跟完。
> **我的结论**：✅ **支持** —— 我原先的"砍跟敲、留原理"是建立在"时间紧张"的假设上，而你每天 6 h、10 月有 180 h，这个假设不成立了。

**为什么改成全量跟完（3 条理由）**

| 理由 | 说明 |
|------|------|
| ① 时间够 | MQ 全量 = **6.86 h 视频 + 约 15~18 h 跟敲 ≈ 25 h**，占你 10 月的 1/7 |
| ② "跟敲过"和"看过"在面试里是两个层次 | 只有自己敲过 Publisher Confirm / manual ack / 死信队列，才能回答"你们怎么保证消息不丢"这种追问 |
| ③ 有现成载体 | "业务改造 + 取消超时订单"是经典场景 —— 可以直接**替换你苍穹外卖里的 `@Scheduled` 定时取消**，变成项目亮点（"我用延迟消息替代了轮询式定时任务"） |

**但必须交产出（否则就是看剧）**
1. 一个 **RabbitMQ demo 仓库**（GitHub）：三种交换机 + 确认机制 + 死信/延迟消息
2. **10 张问答卡**：消息不丢（三环节）/ 不重复消费（幂等）/ 顺序消息 / 消息积压 / 延迟消息 / 死信队列 / 消息确认机制 / 发送者确认 / 持久化 / 消息转换器
3. 一篇博客：**《用 RabbitMQ 延迟消息替换定时任务》**（有对比、有数据）

**节奏（10 月内完成）**：MQ入门 01-16（跟敲 9 集）→ MQ高级 01-13（跟敲 10 集）→ 接进自己项目。
**1 月仍要看 JD**：若目标公司写 Kafka / RocketMQ，再花 5~8 h 补**差异点**（Kafka 分区与顺序、零拷贝；RocketMQ 事务消息、CommitLog），不必重学 MQ 概念。

> 💡 隐藏优势：你在黑马点评里写过 **Redis Stream 消费者组**（建组/ACK/pending/异步秒杀），
> "MQ + 消费者确认 + 幂等"的心智模型可直接迁移到 RabbitMQ —— 你会比同进度的人快一倍。

## 5. 学习方法（比"看多少集"重要）

### 5.1 选课"三问筛选法"（每节课前 10 秒判断）
1. 面试会问吗？　2. 简历项目会用到吗？　3. 不跟敲、以后能不能 30 分钟补回来？
**三问全否 → 只看不敲。**（本路线的三级分类就是这么来的）

### 5.2 跟敲的正确姿势
- **不要边看边敲**：先 1.5x 看完一整节 → 关掉视频自己复现 → 卡住了再回看对应时间点
- 代码**手打，别复制粘贴**，特别是注解位置（`@EnableDiscoveryClient`、`@FeignClient`、`@LoadBalanced`）
- 报错先看异常栈 + 端口占用 / Nacos 是否起来（微服务 90% 的坑是环境和注册问题）

### 5.3 笔记模板（沿用你 Redis 笔记验证过的三件套）
```
🎯 面试点：这个技术解决什么问题、和替代方案对比
💻 本项目实现：关键代码 + 配置片段（只贴决策点，不全贴）
⚠️ 踩坑记录：报错原文 + 原因 + 解决
```
建议新建 `spring cloud\微服务学习笔记.md`，与 `Redis学习笔记.md` 保持同一风格。

### 5.4 必须画的 3 张图（面试直接讲图）
1. **服务拆分图**：黑马商城拆成哪几个服务、各自职责、各自数据库
2. **一次请求的完整链路**：浏览器 → 网关（路由 + 登录校验 + 传递用户）→ 服务 A →（Nacos 服务发现 + 负载均衡）→ 服务 B（Feign 调用）
3. **配置热更新流程**：Nacos 配置中心 → 服务监听 → `@RefreshScope` 生效

### 5.5 每周一个"可展示产出"
例：本周 Nacos 控制台能看到 3 个服务 / 本周网关能路由且登录校验生效 / 本周改配置不用重启就生效。
**没有产出 = 白看**，面试讲的是你做过什么，不是你看过什么。

### 5.6 时间账系数
| 类型 | 系数 | 例 |
|------|------|-----|
| 只看不敲 | × 1.2 | MQ 高级 2.58 h → 约 3 h（含笔记） |
| 跟敲 | × 2 ~ 2.5 | 微服务01 必看 3.38 h → 约 8 h |
| 卡环境/踩坑 | +2 h/次 | **每次都预留缓冲，别把计划排满** |

### 5.7 三条纪律
